# 用户信用分审核演示数据设计

## 目标

在 `/admin/users/list` 的“更多操作 → 信用分审核”中，为 `user_chen（user_1004）` 提供可直接操作的稳定 mock 数据，使待审核处理、状态筛选和历史结果都可演示。

## 范围

- 扩充 `userCreditMembershipRepository` 初始化的信用分审核记录。
- 保留 `user_1004` 为唯一演示用户，避免在用户列表中分散演示入口。
- 不修改审核 Drawer、审核决定 Dialog、MFA 流程、权限或业务校验。
- 不修改全局信用分审核页及其数据。

## 数据设计

`user_1004` 初始化后拥有四条稳定记录：

1. 待审核加分：当前 680 分，建议增加 15 分至 695 分。
2. 待审核减分：当前 680 分，建议减少 20 分至 660 分。
3. 已通过历史：保留审核备注、审核时间和操作人。
4. 已拒绝历史：保留拒绝备注、审核时间和操作人。

每条记录使用唯一且稳定的 ID，`delta` 与 `proposedScore - beforeScore` 一致。待审核记录不包含决定字段；已处理记录包含状态、备注、时间和操作人。列表继续使用现有规则：待审核优先，同组内按申请时间倒序。

## 数据流与状态

页面打开信用分审核时，继续通过 `getUserCreditReviews(userId)` 获取脱离内部状态的副本。处理任一待审核记录后，现有 `decideUserCreditReview` 原子更新该记录；通过时同步更新用户信用分，拒绝时保持当前分数不变，并写入现有审计日志。另一条待审核记录仍可继续演示。

由于两条待审核记录都以初始化时的 680 分为申请基准，实际处理第二条时以该申请的 `proposedScore` 作为通过结果；界面已有确认预览，且本次不改变该既有业务语义。

## 错误与交互

本次不新增交互和错误路径。现有 Drawer、决定 Dialog、MFA、安全关闭、焦点、响应式和错误展示行为保持不变。仅 mock 数据数量和状态覆盖发生变化。

## 测试

- 仓库测试先断言 `user_1004` 有 4 条记录、2 条待审核、1 条已通过、1 条已拒绝，并检查加分与减分场景。
- 断言 ID 唯一、分值关系一致、待审核优先及时间排序稳定。
- 保留现有通过、拒绝、用户归属、一次性处理、原子更新和脱离副本测试。
- 运行信用分仓库测试与信用分组件测试，确认扩充数据不改变现有交互契约。

## 验收标准

从 `/admin/users/list` 找到 `user_chen`，打开“更多操作 → 信用分审核”后：

- 标题显示“待审核 2”。
- “全部”展示四条记录，且待审核记录在前。
- “待审核”展示一条加分和一条减分申请，均可进入处理流程。
- “已处理”展示一条已通过和一条已拒绝记录及审核备注。
- 完成任一审核后，状态、用户信用分和审计记录遵循现有业务规则。
