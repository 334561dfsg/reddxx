# 单用户跨模块控制——业务规则与验收说明

## 1. 文档目的

本文向产品和开发说明单个用户在六个模块中的控制内容、覆盖关系、生效方式、状态和验收场景。本文只定义产品规则，不规定数据表、API、分布式事务或具体算法实现。

## 2. 模块控制总表

| 模块 | 针对单个用户控制什么 | 可选设置 | 单次生效事件 |
| --- | --- | --- | --- |
| 交割 | 控制下一笔或后续交割订单的结算盈亏方向 | 盈利、亏损；单次生效、长期生效 | 下一次符合条件的交割结算 |
| 永续 | 控制下一笔或后续平仓的已实现盈亏方向 | 盈利、亏损；单次生效、长期生效 | 下一次符合条件的平仓、止盈止损或强平结算 |
| 现货 | 控制下一笔或后续卖出交易的已实现盈亏方向 | 盈利、亏损；单次生效、长期生效 | 下一次卖出成交并形成已实现盈亏 |
| AI量化 | 调整用户订单的收益水平 | 高收益、低收益；单次生效、长期生效 | 下一次收益入账或订单结算 |
| 流动性挖矿 | 调整用户挖矿订单的收益水平 | 高收益、低收益；单次生效、长期生效 | 下一次收益入账或赎回结算 |
| 投资组合 | 调整用户投资组合订单的收益水平 | 高收益、低收益；单次生效、长期生效 | 下一次收益入账、到期或赎回结算 |

## 3. 用户点控规则

### 3.1 点控类型映射

用户管理只提供两个点控类型：

| 控盘类型 | 交割、永续、现货 | AI量化、流动性挖矿、投资组合 |
| --- | --- | --- |
| 盈利 | 盈利 | 高收益 |
| 亏损 | 亏损 | 低收益 |

用户点控设置同时覆盖六个模块，并为六个模块分别形成可独立执行的当前规则。

### 3.2 原子结果

用户点控设置必须表现为一个完整操作：

- 六个模块全部设置成功，本次操作才算成功；
- 任一模块设置失败，六个模块均保持操作前状态；
- 不允许出现用户管理提示成功但只有部分模块写入新规则的情况。

### 3.3 覆盖关系

1. 用户管理的新设置覆盖六个模块中该用户的当前规则。
2. 模块点控只覆盖当前模块，其他五个模块保持不变。
3. 同一模块永远以最后一次成功设置为准。
4. 用户管理再次用户点控设置后，会覆盖此前所有模块点控。
5. 所有被覆盖规则保留历史状态，不再参与后续执行。

## 4. 生效方式

### 4.1 单次生效

- 六个模块分别拥有一次执行机会，不是六个模块共用一次。
- 每个模块在下一次符合本模块定义的有效事件中执行。
- 某模块执行成功后，该模块规则变为已执行；其他模块继续等待自己的有效事件。
- 即使业务的自然结果已符合控制要求，也视为该模块的单次规则已执行。
- 事件处理失败、预估收益变化、浮动盈亏、未完成订单和重复通知不消耗单次规则。

### 4.2 长期生效

- 每次符合条件的事件均使用当前规则。
- 执行成功后规则继续生效。
- 只有取消或被新规则覆盖后才停止生效。

## 5. 交易类模块规则

### 5.1 交割

控制目标是交割订单结算后的净盈亏方向。

- 盈利：订单完成结算后，扣除该订单相关费用的已实现净收益大于 0。
- 亏损：订单完成结算后，扣除该订单相关费用的已实现净收益小于 0。
- 单用户规则只处理目标用户订单的最终结算结果，不修改该合约的全局交割价。
- 看涨订单需要盈利时，使用能够让订单结算净收益为正的用户级结算结果；需要亏损时采用相反结果。看跌订单反向判断。
- 同一用户的不同订单分别结算；单笔订单规则可覆盖用户级规则。
- 未付款、已撤销、已作废或结算失败的订单不是有效事件。
- 单次生效规则只在成功完成交割结算后标记为已执行。

### 5.2 永续

控制目标是平仓产生的已实现净盈亏方向。

- 盈利：平仓后，已实现盈亏扣除手续费和资金费用大于 0。
- 亏损：平仓后，已实现盈亏扣除手续费和资金费用小于 0。
- 单用户规则不修改全局K线、标记价格、指数价格或该用户的实时浮动盈亏，只在目标持仓最终平仓结算时处理结果。
- 多仓需要盈利时，最终用户结算结果必须高于包含手续费和资金费的盈亏平衡点；需要亏损时必须低于该点。
- 空仓需要盈利时，最终用户结算结果必须低于包含手续费和资金费的盈亏平衡点；需要亏损时必须高于该点。
- 同一用户同时持有多仓和空仓时，每个持仓独立判断，不尝试使用一条用户级插线同时控制多个持仓。
- 开仓、持仓浮动盈亏、未成交委托和撤单不是有效事件。
- 手动平仓、止盈止损和强平只要成功形成已实现结算，均属于有效事件。

### 5.3 现货

控制目标是卖出交易形成的已实现净盈亏方向。

- 现货采用“双结果模型”：原始交易净盈亏按真实卖出成交、对应持仓成本和费用计算；最终结算净盈亏等于原始交易净盈亏加独立点控调整金额。点控调整金额由系统按现货模块规则自动计算，不是后台点控弹窗的配置项。
- 盈利：最终结算净盈亏大于 0；自然结果不符合时通过独立平台补贴调整。
- 亏损：最终结算净盈亏小于 0；自然结果不符合时通过独立平台扣减调整。
- 单用户规则不修改现货全局行情、K线、盘口、真实成交价、原始成交记录或持仓浮动收益。
- 原始交易净盈亏、损益调整金额和最终结算净盈亏分别记录，调整不得覆盖原始交易数据。
- 每次卖出只计算本次卖出数量对应的成本；不同卖出订单分别判断。
- 买入、持仓估值变化、挂单和撤单不是有效事件。
- 只有完成卖出、能够确定对应成本、点控调整成功入账且最终方向满足规则时，才可执行并消费单次生效规则；调整失败时规则保持待执行。

### 5.4 交易类控制优先级

同一订单或持仓同时命中多个控制时，按以下顺序选择唯一生效规则：

1. 单笔订单或单个持仓的手动控制；
2. 用户级控制；
3. 合约级全局插线或场控；
4. 自然市场结果。

高优先级规则已经决定最终结果后，不再叠加低优先级规则。例如，永续合约正在执行全局插线，但目标用户存在用户级盈利规则，则该用户最终平仓使用用户级规则；如果该用户的某个持仓又单独设置为亏损，则该持仓使用单持仓亏损规则。

单用户控制属于结算级规则，不属于行情级规则：

- 不为目标用户生成单独K线；
- 不修改目标用户看到的实时市场价格；
- 不修改持仓过程中的实时浮动盈亏；
- 只在有效结算事件发生时计算并确认最终已实现结果；
- 单次生效规则只由首笔成功完成的有效结算消费。

## 6. 理财类模块规则

### 6.1 通用定义

理财类不使用“盈利/亏损”，而使用“高收益/低收益”。

- 高收益：该用户本次收益采用订单所属产品配置的高收益区间。
- 低收益：该用户本次收益采用订单所属产品配置的低收益区间。
- 具体收益金额或收益率由各模块依据产品规则、订单本金、周期和产品收益区间计算，后台用户点控不直接输入数值。
- 产品必须先配置可用的高收益区间和低收益区间；缺少对应区间时，本次执行失败且不消耗单次规则。
- 高收益和低收益都必须遵守产品自身的收益边界与展示承诺；保证正收益的产品不能因为“低收益”变为本金亏损。
- 预估收益变化不算有效执行，只有实际收益入账或最终结算成功才算执行。

### 6.2 AI量化

- 控制对象是目标用户的 AI 量化订单。
- 高收益使用该产品允许的高收益档位；低收益使用允许的低收益档位。
- 下一次实际收益入账或订单结束结算，以先成功发生者作为单次生效事件。
- 申购、运行中预估收益和失败入账不消费规则。

### 6.3 流动性挖矿

- 控制对象是目标用户的流动性挖矿订单。
- 高收益和低收益均由产品允许的收益范围决定。
- 下一次实际收益入账或赎回结算，以先成功发生者作为单次生效事件。
- 认购、锁仓中预估收益、取消申请和失败结算不消费规则。

### 6.4 投资组合

- 控制对象是目标用户的投资组合订单。
- 高收益和低收益均由组合产品允许的收益范围决定。
- 下一次实际收益入账、到期结算或赎回结算，以先成功发生者作为单次生效事件。
- 申购、持有期估值变化和失败赎回不消费规则。

## 7. 取消规则

- 用户管理点击取消：取消该用户在全部六个模块中的当前有效规则。
- 模块页面点击取消：只取消该用户在当前模块中的有效规则。
- 已完成的单次生效规则不回退，只保留执行历史。
- 已取消规则不能继续影响后续事件。
- 取消操作必须记录操作人、时间、入口、范围和备注。

## 8. 状态定义

| 状态 | 含义 |
| --- | --- |
| 待执行 | 单次生效规则已设置，等待本模块有效事件 |
| 生效中 | 长期生效规则当前有效 |
| 处理中 | 已进入本次事件处理，尚未得到最终结果 |
| 已执行 | 单次生效规则已在本模块成功执行 |
| 已取消 | 规则被用户管理或模块入口主动取消 |
| 已覆盖 | 规则被更新的用户点控设置或模块点控替代 |
| 执行失败 | 本次事件未成功使用规则；单次生效规则仍保持待执行 |

用户管理汇总状态：

- `6/6 已同步`：六模块来自同一次用户点控设置，策略和生效方式一致。
- `已执行 N/6`：按批次下发的单次生效规则已有 N 个模块正常执行，不属于配置差异。
- `N/6 存在差异`：部分模块被模块点控覆盖或取消，与最近一次用户点控设置不一致。
- `未设置`：六个模块均无当前有效规则。

## 9. 边界规则

1. 控制只影响规则生效后发生的有效事件，不追溯已完成业务。
2. 交易净收益恰好为 0 时，既不算盈利也不算亏损；本次不能标记为成功执行。
3. 缺少成本、持仓、订单或产品收益边界等必要依据时，本次执行失败且不消费单次生效规则。
4. 所有盈亏判断均以相关费用扣除后的已实现净结果为准。
5. 同一模块的单次生效规则在并发事件中只能成功执行一次。
6. 已进入处理的事件使用开始处理时取得的规则；后续取消或覆盖不改变该事件已经采用的规则。
7. 理财模块的低收益不得突破产品本身允许的最低收益和本金规则。

## 10. 日志要求

### 10.1 操作日志

至少记录：目标用户、操作入口、影响模块、修改前规则、修改后规则、生效方式、操作人、操作时间和备注。

### 10.2 执行日志

至少记录：目标用户、模块、业务单号、规则内容、生效方式、规则来源、执行结果和执行时间。

交易类记录执行前后盈亏方向；理财类记录执行前后收益档位。产品如需记录具体金额或收益率，由各模块后续设计确定。

## 11. 验收场景

1. 用户管理设置“盈利 + 单次生效”后，交易三模块显示盈利，理财三模块显示高收益，六模块均为待执行。
2. 用户管理设置“亏损 + 长期生效”后，交易三模块显示亏损，理财三模块显示低收益，六模块均为生效中。
3. 用户点控设置时任一模块失败，六个模块均保持操作前规则。
4. 交割的单次生效规则执行完成后只更新交割状态，其他五个模块仍待执行，汇总显示“已执行 1/6”。
5. 永续模块独立改为相反方向后，只更新永续，汇总显示“5/6 存在差异”。
6. 用户管理再次用户点控设置后，六个模块全部使用新规则，恢复为“6/6 已同步”。
7. 用户管理取消后，六模块当前规则全部取消；模块页面取消后只有当前模块取消。
8. 交易事件净收益为 0、结算失败或缺少成本依据时，单次生效规则不消费。
9. 理财预估收益变化不消费规则，实际入账或最终结算成功后才消费。
10. 理财低收益不会突破产品最低收益边界，也不会让保证正收益的产品产生本金亏损。
11. 所有设置、覆盖、取消、成功执行和失败执行均可通过日志追溯。
12. 永续全局插线与用户级规则同时存在时，目标用户最终结算使用用户级规则，其他用户继续使用全局场控结果。
13. 单个永续持仓的手动控制与用户级规则冲突时，单持仓规则生效。
14. 永续用户级规则生效前后，K线、实时价格和持仓浮动盈亏展示保持不变，只有最终平仓结算结果按规则确认。
15. 同一用户同时持有多仓与空仓时，每个持仓分别按自己的方向判断盈利或亏损。
16. 交割与现货的用户级规则同样不改变全局行情，只处理目标订单的最终已实现结果。

## 12. 非目标

本文不定义最终结算结果的技术生成方式、收益计算公式、金额档位、数据库结构、API、事务实现、权限系统或结算服务架构。上述内容应由各模块开发团队在不改变本产品规则的前提下另行设计。
