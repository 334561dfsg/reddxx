# Project Agent Instructions

These instructions apply to every agent and every change in this repository.

## Responsive and adaptive interaction constraints

All responsive and adaptive work must preserve the same core business capabilities, data results, authorization, validation, error handling, safety confirmations, and status feedback across PC, tablet, and mobile. A low-frequency or secondary capability may be collapsed, collected, or converted into another component, but it must not be removed and must remain discoverable and accessible; do not use `display: none` to hide a capability users still need.

1. Adapt according to available space, content, input capability, and user preference, not device names or User-Agent alone. Choose a breakpoint when content can no longer remain usable, rather than tying it mechanically to a device model. Component form may change without changing business semantics, submission result, default value, or risk level.
2. A desktop Dialog may become a bottom or full-screen Drawer, and a side Drawer may become a full-width or bottom Drawer. Preserve the title, intentional close path, focus, backdrop, scroll, submission, and error semantics, and apply the applicable Dialog and Drawer constraints. Hover-only information must have click and keyboard access; drag, swipe, long-press, and precision-pointer interactions need a simple click or keyboard alternative.
3. A breakpoint change, window resize, or orientation change must retain unsubmitted form data, filters, searches, pagination, selections, expanded items, upload progress, and business context. When an open overlay changes form, retain exactly one active instance: no duplicate backdrops, requests, callbacks, focus traps, or scroll locks. Move focus to equivalent content or action, or a reasonable title/first action when no equivalent target remains. Never interrupt a submission, upload, or uninterruptible operation.
4. Support desktop, laptop, tablet, narrow and landscape phones, low-height viewports, 200% browser zoom, system text enlargement, dynamic browser chrome, virtual keyboard, and all `safe-area-inset-*` directions. Core content and actions must remain reachable without a key flow requiring two-dimensional scrolling. Fixed headers, footers, and floating actions must not fully obscure the focused element, error message, or primary action; dynamic viewport units need a reasonable fallback and scrolling must remain clear and predictable.
5. Do not assume desktop means mouse-only or mobile means touch-only. Core actions must work with keyboard, mouse, and touch, retain a visible focus indicator, and be usable without precision tapping. Keyboard Focus must expose hover-supplemented information; an interactive floating surface must remain usable when the pointer moves into it.
6. Prioritize titles, amounts, states, errors, and primary actions. Support long headings, words, translated text, and enlarged fonts without losing meaning or access to an action. Do not convey important information only by icon, placement, color, or hover; use descriptive names for collapsed entries.
7. For each change, verify the applicable viewport, input, orientation, zoom, virtual keyboard, safe-area, reduced-motion/high-contrast, long-text, and active-state breakpoint cases. Any interaction, input method, or viewport not actually checked must be reported as unverified with the required check; never state that an unperformed check passed.

The full cross-platform standard is [responsive-adaptive.md](https://github.com/gloopai/frontend-product-interaction-standards/blob/main/references/responsive-adaptive.md). Apply it together with the component-specific rules; where compatible rules differ in strictness, follow the stricter rule.

## Searchable single-select constraints

These requirements apply to custom, searchable, single-select controls whose business value must come from an existing option. They do not cover multi-select, tags, free-text creation, trees, cascaders, date pickers, or complex options with independent interactive controls. The full standard is [selects-comboboxes.md](https://github.com/gloopai/frontend-product-interaction-standards/blob/main/references/selects-comboboxes.md); the requirements below remain independently enforceable.

1. Keep `selectedValue`, its resolved option, `query`, `activeOption`, `open`, loading, error, and `searchPlacement` state separate. `searchPlacement` is `auto`, `inline`, `panel`, `drawer`, or `none`; business may set it explicitly, while `auto` must use option scale, search frequency, need to keep the selected value visible, available space, input method, and virtual-keyboard impact—not agent preference or a brittle fixed threshold. Above roughly seven options, assess type-ahead or search. `selectedValue` may only be an existing valid option value or an explicitly permitted empty value. Typing, filtering, keyboard highlighting, hover, opening, async refreshes, a newly arrived first result, and a search-location/breakpoint change must never implicitly commit or clear it.
2. `inline` uses its main input as an Editable Combobox for frequent name/code/UID lookup. `panel` uses a visible-selected-value trigger button and puts the controlling search Combobox at the top of the PC popup; never mislabel that trigger as an Editable Combobox. `drawer` uses an external trigger and a controlling search Combobox below the Drawer fixed title, for mobile, large lists, or virtual-keyboard pressure; also apply the Drawer rules. `none` shows no search box: use a Select-only Combobox or button + listbox with keyboard type-ahead, never a fake search field. All modes share state; mode or breakpoint changes retain one instance without clearing a selected value, repeating requests/callbacks, or duplicating overlays/focus traps/scroll locks.
3. A user commits a value only by explicitly choosing an enabled option, pressing `Enter` on it, or using a separately named, business-permitted clear action. Opening with a selected value highlights it; opening without one may highlight the first option but never select it. Outside close, `Escape`, and an allowed Drawer close button discard the current uncommitted query/highlight and preserve the committed value; `Tab` closes while continuing normal tab order. Disabled controls cannot focus or open; read-only controls cannot search, clear, or select. Prevent duplicate open, close, select, and callback execution.
4. Support `ArrowDown`/`ArrowUp` to open or move the active enabled option, `Enter` to select it, `Escape` to close, and `Home`/`End` to move to the first/last option. Printable input searches in modes that display a search field; Backspace, Delete, left/right arrows, and platform text-editing shortcuts retain native single-line text-editing behavior. In `none`, printable input is type-ahead. Focus movement is never selection.
5. `inline`'s main input, and `panel`/`drawer`'s controlling search input, use `role="combobox"`, a visible contextual label via `<label>` or `aria-labelledby`, `aria-expanded`, `aria-controls`, `aria-autocomplete="list"`, and `aria-activedescendant` while open with an active option. Search labels must be contextual (for example, “Search currency” or “Search user”), not a generic placeholder. The `panel`/`drawer` trigger is a button with an accessible name and appropriate expanded/controls semantics, not an Editable Combobox. Set `aria-required="true"` when required; set `aria-invalid="true"` and associate a textual error when invalid. Use a `role="listbox"`; each option needs a stable unique ID, `role="option"`, and correct `aria-selected`. Keep DOM focus at the controlling PC combobox while its listbox is open, and do not put buttons, links, or other independent controls inside options.
5. Local search filters immediately and restores all results when `query` clears. Remote search should debounce about 250ms and must cancel earlier work or ignore stale results using a request sequence/query key. Query changes, stale results, failures, pagination, and refreshes must not clear or replace the selected value, reorder options unpredictably, or change the active option unexpectedly. Keep the control open on failure and provide textual error and retry feedback; expose loading, result count, no-result, and error status accessibly.
6. Preserve a selected option that is absent from current results. If a data refresh invalidates the selected value, visibly mark it invalid and require reselection; never silently clear or substitute another option. Make duplicate labels distinguishable and disabled options visibly unavailable.
7. On PC, use a non-modal popup anchored to the `inline` combobox, `panel` trigger, or `none` control, at least anchor width, constrained within the viewport, able to flip above/below, and not clipped by an overflow ancestor (portal to the application root when needed). In `panel`, keep the controlling search Combobox at the popup top. When present, keep the search area and status fixed-visible; only the option region scrolls. A first open fades with a small translation over `150ms ease-out`; closing reverses it over `100ms ease-in` and unmounts after the animation. When reduced motion is requested, omit translation and use fades of 50ms or less or no motion.
8. `drawer` uses an external trigger and a bottom Drawer with the controlling search Combobox below the fixed title. Keep that search area visible while only options scroll, and preserve one active instance plus the same selected value, query, active option, data source, errors, and request state. Use Drawer requirements for backdrop, intentional close paths, fixed non-scrolling frame, close button, focus, background isolation, safe areas, scrolling, and Drawer animation. A search-location or breakpoint change must not duplicate overlays, requests, callbacks, focus traps, scroll locks, or enter/exit animations, and must move focus to an equivalent search field, trigger, or reasonable title.
9. Large result sets may use a virtual list only when the option referenced by `aria-activedescendant` exists in the DOM and is scrolled into view; expose result count and position. Pagination/infinite loading must not duplicate options, drop the selected value, or unexpectedly move the active option.
10. Verify `auto` resolution and each `inline`, `panel`, `drawer`, and `none` mode, including mode/breakpoint runtime transitions; applicable mouse, touch, keyboard, type-ahead, screen-reader, PC popup, mobile Drawer, virtual keyboard, low-height, safe-area, 200% zoom, long-text, reduced-motion, async-race, and error cases. Any interaction, input method, assistive technology, or viewport check not performed must be reported as unverified with the required follow-up check.

## Dialog interaction constraints

All dialogs, modals, and dialog-like popups must meet these required acceptance criteria. Preserve them during refactors and verify relevant interactions and viewport sizes; any interaction or viewport behavior not actually tested must be reported as unverified with the required check.

1. Backdrop clicks must never close a dialog or start its closing animation. Do not add backdrop-close handlers; disable the equivalent UI-library option. A dialog closes only through an intentional in-dialog action. The outer frame must remain non-scrolling (`overflow: hidden`): constrain its height and let only the body/content region scroll (`overflow-y: auto`), keeping headers, footers, and actions in the fixed frame. The viewport-fixed overlay (`position: fixed; inset: 0`) must cover the full viewport at the application root when needed, never a local panel, transformed ancestor, or other clipped container.
2. Opening uses an overlay fade and dialog fade/`scale(0.96)` to `scale(1)` over `200ms ease-out`; closing reverses it over `150ms ease-in` and unmounts only after completion. Block duplicate open/close actions during motion, and retain the overlay, focus containment, and scroll lock through the close animation. With `prefers-reduced-motion: reduce`, omit scaling and use fades of at most `50ms` or no animation.
3. On open, focus the appropriate in-dialog target: the first reasonable action in ordinary forms, the title/top static element for long content, or the least destructive action for irreversible work. Keep `Tab` and `Shift + Tab` within the active dialog. After the close animation, return focus to the trigger or a logical next-flow target if it no longer exists. `Escape` normally closes only the topmost dialog; while submitting, in an uninterruptible flow, or with unsaved work, disable Escape or require confirmation.
4. While open, background content must be unavailable to pointer, touch, keyboard, and assistive technology through native modal behavior or an equivalent such as `inert`. Use `<dialog>`, or `role="dialog"` with `aria-modal="true"`; provide an accessible name through a visible title and `aria-labelledby` when possible, falling back to `aria-label` only when no visible title exists. Do not put complex full content in `aria-describedby`. Provide a visible, focusable, accessibly named close, cancel, confirm, or equivalent action. Every ordinary dialog that users may exit must also keep a visible close button in its fixed top-right header; footer cancel, close, confirm, or other actions do not replace it. Use a clear close icon with `aria-label="关闭"`, keyboard focus, and an adequate pointer/touch target; it must remain visible while content scrolls, titles wrap, and layouts adapt to mobile or low-height viewports, and it must follow the same safe close path as cancel. Hide or disable it only when submission is explicitly uninterruptible, confirmation is mandatory, a security flow forbids exit, or another documented business rule disallows closing; agents and developers must not omit it by preference.
5. With layered dialogs, only the topmost dialog is interactive; every lower layer and the page background stay inert. On closing the top layer, restore focus to its trigger in the underlying dialog. Use a shared layer system rather than arbitrary local `z-index` values.
6. During async work, prevent duplicate submission, close, and callback execution. Loading controls retain accessible names and expose needed state to assistive technology. On failure, keep the dialog open, present a textual error, and move focus or provide an error summary at a sensible location; never auto-close before the error can be read. If interruption is disallowed, clearly disable the relevant closing paths and communicate that state.
7. Controls and focused elements must remain reachable at zoom, on mobile, in low-height viewports, and with a virtual keyboard; they must not be fully hidden by fixed headers, footers, or the keyboard. Avoid fixed pixel heights and provide fallbacks for dynamic viewport units. On close, route change, or unmount, clear scroll lock, `inert`, focus traps, event listeners, and animation state. Reopening must not retain stale overlays, loading, errors, or closing state.

Recommended design: keep destructive-action button order stable, use task-specific titles rather than generic “Notice” or “Information,” clear old loading and error state on reopen unless intentionally retained, and avoid complex navigation inside simple confirmations. See the [WAI-ARIA modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [MDN dialog element guidance](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog), and the [full Dialog interaction standard](https://github.com/gloopai/frontend-product-interaction-standards/blob/main/references/dialogs.md).

## Drawer interaction constraints

All modal Drawers, Sheets, and slide-out panels from the left, right, top, or bottom must meet these required acceptance criteria. Preserve them during refactors and verify relevant interactions and viewport sizes; any interaction or viewport behavior not actually tested must be reported as unverified with the required check. Ordinary non-modal sidebars, fixed navigation, and page splits without an overlay relationship are not modal Drawers.

1. A modal Drawer uses a viewport-fixed backdrop (`position: fixed; inset: 0`) at the application root or an equivalent unclipped layer. It must cover the full viewport, never a local panel, positioned ancestor, or transformed container. Backdrop clicks must never close the Drawer or start its closing animation; disable equivalent UI-library behavior. Drag, swipe, and drag-handle gestures must never close it. Except for the `Escape` keyboard path in item 4, when that path is allowed by the business state, a Drawer closes only through an intentional in-Drawer close button, cancel, confirm, or explicit business action; backdrop, drag, and swipe are never closing paths.
2. The Drawer frame remains non-scrolling (`overflow: hidden`): constrain its available size and let only its content region scroll (`overflow-y: auto`). Keep the header, fixed top-right close button, footer actions, and necessary status region in the frame so they cannot scroll out of view. Every ordinary Drawer users may exit must provide an always-visible, focusable close icon in its fixed header top-right with `aria-label="关闭"`, adequate pointer/touch target, and the same safe close path as cancel. Footer actions do not replace it. Hide or disable it only for an explicitly uninterruptible submission, mandatory confirmation, security flow, or documented business rule, and communicate why exit is unavailable.
3. Left Drawers are fixed to the left edge and enter left-to-right, then exit to the left; right Drawers mirror that behavior. Top Drawers are fixed to the top edge and enter top-to-bottom, then exit upward; bottom Drawers mirror that behavior. Open with backdrop fade plus edge-aligned translation over `200ms ease-out`; close with the reversed translation and fade over `150ms ease-in`, unmounting only after completion. Block duplicate opens, closes, and callbacks during motion and retain backdrop, focus containment, background isolation, and scroll lock through the close animation. With `prefers-reduced-motion: reduce`, omit translation and use fades of at most `50ms`, or no animation.
4. On open, focus the title/top static element for long content, the first reasonable action for ordinary forms, or the least destructive option for irreversible work. Keep `Tab` and `Shift + Tab` within the topmost Drawer. `Escape` normally closes only the topmost Drawer; while submitting, in an uninterruptible flow, or with unsaved work, disable Escape or require confirmation. After the close animation, return focus to the trigger or a logical next-flow target if that trigger no longer exists.
5. While a modal Drawer is open, background content must be unavailable to pointer, touch, keyboard, and assistive technology through native modal behavior or an equivalent such as `inert`, and page scrolling must be locked. Use native modal behavior, or `role="dialog"` with `aria-modal="true"` and an accessible name, preferably a visible title linked by `aria-labelledby`; use `aria-label` only with no visible title. Do not put complex full content in `aria-describedby`. Non-modal Drawers must not claim `aria-modal="true"` or isolate the background without cause.
6. With layered Drawers, or a Drawer layered with a Dialog, only the topmost layer is interactive; every lower layer and the page background remain inert. On closing the top layer, restore focus to its trigger in the underlying layer. Use a shared layer system rather than arbitrary local `z-index` values.
7. During async work, prevent duplicate submission, close, and callback execution. Loading controls retain accessible names and expose needed state to assistive technology. On failure, keep the Drawer open, present a textual error, and move focus or provide an error summary at a sensible location; never auto-close before the error can be read. If interruption is disallowed, clearly disable every relevant closing path and communicate that state.
8. Constrain left/right Drawer width and top/bottom Drawer height without relying on fixed pixel heights that hide content or actions. Ensure controls and focus targets stay reachable on mobile, at zoom, in low-height and dynamic viewports, and with a virtual keyboard. Respect the corresponding `safe-area-inset-top`, `safe-area-inset-bottom`, `safe-area-inset-left`, and `safe-area-inset-right` regions.
9. Before activating a new Drawer instance, clear the prior instance's stale overlay, loading, error, closing, and animation state, plus listeners or effects that should no longer exist. While the current Drawer is open, establish and retain its required scroll lock, background isolation (including `inert`), focus trap, and listeners; reopening must not clear these current valid protections. Only after the current close animation completes, or on route change or unmount, clear its scroll lock, `inert`, focus traps, listeners, animation state, and temporary loading, error, and closing state. Verify all four directions, backdrop/drag/swipe resistance, fixed-frame scrolling, close controls, focus, Escape, semantics, background isolation, layering, async errors, reduced motion, safe-area behavior, and cleanup. Report any untested interaction or viewport behavior as unverified and state the required check.
